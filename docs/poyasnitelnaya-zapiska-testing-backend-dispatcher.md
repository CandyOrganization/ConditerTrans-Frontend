# 3.3.2 Тестирование серверной части приложения (роль «диспетчер производства»)

Тестирование серверной части информационной системы ConditerTrans выполнялось для проверки корректности работы REST API-маршрутов, взаимодействия сервера с базой данных **PostgreSQL** и выполнения прикладной логики в сервисах и репозиториях. В отличие от архитектуры на хранимых процедурах, доступ к данным реализован через **Entity Framework Core** (LINQ-запросы в `OrderRepository`); поэтому проверялись как **операции выборки** (списки заказов, карточки, аналитические отчёты), так и **операции модификации** (смена статусов заказа, создание груза, запись истории изменений).

Серверная часть принимает HTTP-запросы от веб-клиента диспетчера, выполняет авторизацию по JWT, вызывает методы `OrderService` и обращается к БД через репозитории; результат возвращается в формате **JSON**. Тестирование проводилось на тестовом стенде с наполненной БД (скрипты `docs/database/seed-companies-5x3.sql`, `seed-load-test.sql`).

### Средства и методика тестирования

| Средство | Назначение |
|----------|------------|
| **Swagger UI** (`/swagger`) | Вызов API-маршрутов с телом запроса и просмотр кодов ответа |
| **Postman / встроенный HTTP-клиент IDE** | Повторяемые запросы с заголовком `Authorization: Bearer {token}` |
| **DataGrip** | Проверка соответствия данных в таблицах `orders`, `order_change_histories`, `cargos` после модифицирующих операций; выполнение аналитических SQL-запросов (раздел 3.1.1) |
| **Веб-клиент диспетчера** | Сквозная проверка: ответ API отображается на экранах «Заказы», «Карточка заказа», «Отчёты» |

**Учётная запись для тестов:** `seed-dispatcher-1@load.test`, пароль `Password1!` (диспетчер производства компании из seed-данных).

**Порядок проверки модифицирующих операций:** для каждого сценария использовался отдельный заказ в подходящем статусе; после POST-запроса выполнялась проверка HTTP-кода (200/204), тела JSON и выборка из БД (`SELECT status, … FROM orders WHERE id = …`).

| 10 | `POST /api/orders/dispatcher/{id}/handover` | Фиксация передачи документов логисту | Статус → Shipped | Заказ переведён в Shipped, изменение зафиксировано в истории |
| 11 | `GET /api/orders/dispatcher/reports/refusals` | Запрос отчёта по отказам за период (`dateFrom`, `dateTo`) | JSON `{ result: [{ reason, orderCount, sharePercent }] }`; учитываются только заказы Rejected данного производства | Отчёт сформирован (HTTP 200), группировка по причинам и доли в процентах совпадают с контрольным SQL в DataGrip |
| 12 | `GET /api/orders/dispatcher/reports/product-rating` | Запрос рейтинга продукции за период | JSON `{ result: [{ rank, name, orderCount }] }`; учитываются заказы Confirmed | Рейтинг сформирован, порядок по убыванию `orderCount` корректен; данные совпадают с SQL-запросом из раздела 3.1.1 |
| 13 | `GET /api/orders/dispatcher` | Запрос под учётной записью менеджера (не Dispatcher) | HTTP 403 Forbidden | Доступ к маршрутам диспетчера без роли Dispatcher отклонён |
| 14 | `POST /api/orders/dispatcher/run-deadline-check` | Ручной запуск проверки дедлайнов готовности | Обработаны заказы с истекающим сроком подтверждения; обновлены поля `deadline_confirmation_*` или статус при автоматическом отказе | Фоновая логика отрабатывает по расписанию; ручной вызов даёт ожидаемое изменение состояния тестовых заказов |

### Дополнительные проверки взаимодействия с БД

После модифицирующих операций (п. 6–10) выполнялись контрольные выборки:

```sql
-- статус и диспетчер заказа
SELECT id, status, dispatcher_id, cargo_id
FROM orders
WHERE id = '…';

-- последняя запись истории
SELECT order_status, change_time, comment
FROM order_change_histories
WHERE order_id = '…'
ORDER BY change_time DESC
LIMIT 5;

-- созданный груз
SELECT id, status, length_m, width_m, height_m, weight_kg
FROM cargos
WHERE id = (SELECT cargo_id FROM orders WHERE id = '…');
```

Для аналитики (п. 11–12, 15–16) использовались SQL-запросы, эквивалентные методам репозитория (см. раздел 3.1.1 и файл `docs/database/`).

### Выводы по результатам тестирования

В таблице 47 приведены основные проверки серверной части в части роли **диспетчера производства**. Для каждой проверки указаны проверяемый маршрут или компонент, выполняемое действие, ожидаемый и фактический результат.

По результатам тестирования установлено, что серверная часть:

- корректно обрабатывает HTTP-запросы и возвращает данные в формате JSON;
- обеспечивает авторизацию и разграничение доступа по роли и `CompanyId` из JWT;
- выполняет операции выборки через EF Core с фильтрацией заказов по принадлежности товаров производству;
- корректно изменяет статусы заказов, создаёт грузы и записывает историю в `order_change_histories`;
- формирует аналитические отчёты, согласованные с контрольными SQL-запросами в PostgreSQL.

Для проверки серверной части использовались **тестовые HTTP-запросы** (Swagger, Postman) и **выполнение SQL-запросов в DataGrip** (аналог контрольных выборок в СУБД). Результаты проверки аналитических запросов выборки данных приведены в подразделе **3.1.1**; скриншоты запросов, ответов API и планов `EXPLAIN ANALYZE` могут быть вынесены в приложение к пояснительной записке.

По итогам тестирования серверные маршруты диспетчера производства работают в соответствии с техническим заданием: заявки на закупку обрабатываются производством (подтверждение, отказ, перенос), готовность к отгрузке фиксируется с созданием груза, передача логисту отражается в статусе заказа, аналитика по отказам и рейтингу продукции доступна за выбранный период.
